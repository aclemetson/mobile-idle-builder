# Notifications

**Scope:** OS notifications on Android and iOS, in two kinds:
- Local notifications are scheduled on the device from the save when the player leaves.
- Remote push campaigns are sent from the Unity dashboard through UGS Push Notifications.

Both use the same OS permission and the same Settings toggle.

> Verified against: `feat/surge-notification-exact-alarms`, 2026-11-21.

## Lifecycle

- **Leaving the app** (`OnApplicationPause(true)` / quit): `SaveManager` writes the save, then raises
  `SaveManager.Backgrounding`. `NotificationService` cancels everything pending and schedules the new plan,
  but only while `IsActive` (the `notifications.enabled` flag is on, the Settings toggle is on and OS permission is granted).
  It does not use its own pause handler for this, so it always reads the state that was just saved.
- **Coming back** (Awake / `OnApplicationPause(false)`): cancels all scheduled and delivered notifications and
  clears the iOS badge, so nothing fires while the player is in the game. If the app was opened from a
  notification, logs `notification_opened_local`.
- Failures are caught and logged; a notification problem never breaks the save path.

## What gets scheduled

| Kind | Channel | When | Source |
|---|---|---|---|
| `StorageFull` | production | now + `OfflineCollectionService.GetEffectiveIdleCap` (after the tutorial) | idle cap |
| `ResearchDone` | production | `activeResearchCompleteUtc` | research timer |
| `CraftDone` | production | `CraftQueue.SecondsRemaining` | recipe craft queue |
| `CyclotronReady` | production | `CyclotronProgress.CooldownLeft`, only if `IsUnlocked` | Cyclotron Kick |
| `BoostEnded` | boosts | `BoostLock.Remaining` (when every timed boost has ended) | speed burst, Idle ad boost, Cyclotron boost |
| `DailyReward` | rewards | next UTC midnight if today's reward was claimed, else in 4 h (before the reset) | `lastLoginRewardUtc` |
| `RewardsExpiring` | rewards | 2 h before the daily/weekly/monthly reset, only if `AchievementService.HasClaimable` for it | achievement resets |
| `SurgeReady` | boosts | latest of: Entropy Surge cooldown, `BoostLock` (when it blocks the ad), the daily-cap reset (00:00 UTC, only when today's watches are used up), and `SurgeMinAway` (2 h). Only after the first prestige and with `ads.enabled` on | `adLastWatch`, `adWatchCounts` (`NotificationInputs.SurgeReadyDelay`) |
| `Comeback24h` / `Comeback72h` | reminders | now + 24 h / 72 h (after the tutorial) | none |

The rules live in `NotificationPlanner` and are covered by the tests:
- Anything less than 60 s away is skipped.
- Quiet hours run from 22:00 to 08:00 device local time; anything that would land in them moves to 08:00.
- Production alerts within 15 min of each other merge into one `ProductionCombined` ("Your foundry needs you"), fired at the latest time.
- At most 3 notifications land in any 24 h, kept in priority order: storage > combined > research > craft > Cyclotron > boost > rewards expiring > daily > surge > comeback.
- The surge reminder has a 2 h floor so a 15 min cooldown does not ping everyone who closes the app right after a surge. It cannot know whether an ad will be loaded, and the HUD icon waits a few seconds for income to be measured after launch.

**Clocks:** the delays are measured against `GameClock.UtcNow` (the timers' own clock), and the fire time is
`DateTime.UtcNow + delay`, because the OS fires on the wall clock. That way a playtest clock offset never
moves an OS alarm. Achievement and daily resets are server/wall time, so they use `DateTime.UtcNow` directly.

Ids are stable per kind (`1000 + kind`). Android sends with an explicit id, iOS uses that id as the identifier.

## Permission and settings

- **Opt-in card.** Checked once per launch by `NotificationService.TickPrompt`, with the rule in
  `NotificationAskPolicy` (unit tested):
  - Asks when never asked (`SettingsData.notificationPromptShown` false), or on the first startup after
    `notificationNextAskUtc` (30 days after the last answer, either answer).
  - Never asks once "Don't ask again" was ticked (`notificationNeverAsk`), or while notifications are already
    on (OS permission granted and the Settings toggle on).
  - Shows about 8 s after the game is playable (`SaveData.tutorial.isActive == false` and `ECSLoadBridge.IsLoaded`,
    so a new player gets it right after the tutorial), when no dialogue, `ConfirmPrompt` or save-conflict prompt
    is open. It uses `ConfirmPrompt` with the `NotificationTexts.Prompt*` copy, a neutral button and the
    optional checkbox (`checkboxLabel`, read back from `ConfirmPrompt.CheckboxChecked`).
  - "Notify me" turns the toggle on, then shows the OS prompt, or opens the OS notification settings if the
    OS already denied it.
  - "Not now" shows no OS prompt, so the OS one-time ask is saved for later.
  - `notif prompt` in the dev console resets all four fields (including `exactAlarmAsked`) and shows the card.
- **On-time reminders card (Android exact alarms).** `NotificationTexts.Exact*`, rule in
  `NotificationAskPolicy.ShouldAskExact`. Shown once ever (`SettingsData.exactAlarmAsked`, either answer), only while
  notifications are on and `INotificationPlatform.ExactAlarmsNeedGrant` (Android 12+ without "Alarms & reminders").
  - Right after the player allows notifications (opt-in card or Settings toggle), 0.5 s after the OS dialog closes.
  - At startup, in place of the opt-in card, for players who already had notifications on.
  - "Open settings" calls `AndroidNotificationCenter.RequestExactScheduling` (the OS page for this app). The OS page
    is the only place to grant it; the next background picks up the new state.
  - Telemetry: `notification_permission` with source `exact_<after_opt_in|startup>` (opened) or `..._declined`.
  - `notif exact` in the dev console shows it now.
- **`SettingsService`** self-bootstraps (`BeforeSceneLoad`); it is not placed in any scene. Until it did, it was
  never created in builds, so every setting, the notification toggle included, read as missing.
- **Settings toggle** `toggle-notifications` (`HUDSettingsSubController`) calls `NotificationService.SetEnabledFromSettings`:
  - Off: cancels everything.
  - On, never asked: shows the OS prompt.
  - On, denied: opens the OS notification settings, because the OS won't ask twice.
  - The toggle displays `IsActive`, not just the saved preference.
- **Android:** target SDK is automatic (33+), so `POST_NOTIFICATIONS` is a runtime permission; the package adds the manifest entry.
  - Four channels: `qf_production`, `qf_boosts` and `qf_rewards` at default importance, `qf_reminders` at low (silent). Players can mute each channel in OS settings.
  - **Exact alarms:** "Schedule at exact time" is `ExactWhenAvailable | AddScheduleExactPermission` (`3` in
    `NotificationsSettings.asset`), which adds `SCHEDULE_EXACT_ALARM` only. `USE_EXACT_ALARM` (auto-granted) is NOT
    added: Play restricts it to alarm-clock and calendar apps. When the OS allows exact alarms (below Android 12
    always; Android 12/13 by default; Android 14+ only after the player grants "Alarms & reminders"), the package
    schedules `setExactAndAllowWhileIdle` (on time, also under Doze and Battery Saver) and
    `AndroidNotificationPlatform.Schedule` skips the window plugin for game events. Comeback reminders still get
    the 1 h window, to save battery.
  - **Delivery window (no exact grant):** the package's inexact alarm may be up to an hour late. Every `PlannedNotification` has a
    `MaxLateness` from `NotificationPlanner.MaxLatenessFor` (10 min for game events, 1 h for comeback reminders),
    one rule for all platforms. On Android, `Assets/Plugins/Android/NotificationAlarmWindow.java` replaces the
    package's alarm with `AlarmManager.setWindow` (no permission; 10 min is the Android 12+ minimum). It finds the
    alarm by the package's PendingIntent (receiver `UnityNotificationManager`, request code = notification id), so
    re-check it after updating `com.unity.mobile.notifications`. Best effort: if it fails, the inexact alarm still fires.
    `adb shell dumpsys alarm` shows `window=+10m0s0ms` on the game's alarms when it works. iOS triggers already fire on time.
  - **Power saving:** Battery Saver holds plain alarms (`set`, `setWindow`) until it is turned off (`dumpsys alarm` shows
    `battery_saver=+364d...`). When power saving is on at scheduling time, the plugin uses `setAndAllowWhileIdle`
    instead, which still fires (OS-chosen time). Saver turned on later still holds the windowed alarms.
  - "Reschedule on Device Restart" is on, which adds `RECEIVE_BOOT_COMPLETED`.
- **iOS:**
  - "Request Authorization on App Launch" is OFF (the package default is on): we ask ourselves, after the tutorial.
  - Badge 1 per notification, cleared on open.
  - Local notifications need no Push capability or entitlement.

## Remote push (UGS Push Notifications)

- **Package:** `com.unity.services.push-notifications` 4.0.2. It uses `com.unity.mobile.notifications` underneath and delivers through FCM on Android and APNs on iOS. Android minSdk is 26 because of it.
- **When the device registers:** `RemotePushService` (self-bootstrapped) calls `RegisterForPushNotificationsAsync` once per launch, when all of these hold:
  - the `push.enabled` flag is on
  - UGS is initialized
  - analytics is collecting (`analytics.enabled`)
  - the Settings toggle is on
  - OS permission is already granted

  `notificationServices` is UGS's analytics event that carries the push token. Without analytics collection it is never sent, so the dashboard cannot target the device. The SDK's own request finds the permission already granted, so the player only ever sees our single prompt.
- **Receiving:** a campaign that arrives while the game is open shows as the HUD banner (`HUDController.ShowNotification`). In the background, the OS shows it and tapping opens the game. The SDK records `notificationOpened` itself.
- **Opting out:** the SDK has no unregister call. Turning the toggle off sends `notification_preference{enabled:false}`, and campaign audiences should exclude those players. The OS settings are the hard off switch.
- **iOS:** the push package's post-build step (`IOSBasicPushNotificationPostProcess`) adds:
  - the Push capability with the **production** `aps-environment`
  - the `remote-notification` background mode
  - `UNITY_USES_REMOTE_NOTIFICATIONS`

  TestFlight and App Store builds use production APNs, so the dashboard's Apple key must have Sandbox = false. Xcode debug installs will not receive campaigns.

  **Required:** Project Settings > Mobile Notifications > iOS > "Enable Push Notifications" (`UnityAddRemoteNotificationCapability` in `ProjectSettings/NotificationsSettings.asset`) must be on, with "Use APS Release Environment" on. The native code skips `registerForRemoteNotifications` when that Info.plist key is false, so the push SDK gets an empty token, throws "Failed to register", and no `notificationServices` event is sent (found on 0.6.37). Keep the two "request authorization on app launch" options off: we ask after the tutorial.

  `IOSRichPushNotificationPostProcess` also adds a Notification Service Extension target, `notificationservice` (bundle id `<app id>.notificationservice`, for images in pushes). Cloud signing (`-allowProvisioningUpdates` with the Admin App Store Connect key) creates its App ID and profile. Package 4.0.2 writes that target's ARCHS without the closing parenthesis; `Assets/Scripts/Editor/IOSPushExtensionFix.cs` (order 2) repairs it. Re-check both after a push package update.
- **Dev console:** `push status` shows whether the device is registered, why not if it isn't, and the device token (paste it into the dashboard's "Test on Device").
- **Sending campaigns, and the key setup:** see `docs/runbooks/push-campaigns.md`.

## Kill switch and telemetry

- `notifications.enabled` and `push.enabled` (Remote Config, default `true`). See `feature-flags.md`.
- Events `notification_permission`, `notification_preference` and `notification_opened_local`. See `analytics.md`; register the schemas in the dashboard.

## Adding a notification

1. Add a `NotificationKind`. Append it at the end: ids derive from the enum value, so inserting one in the middle shifts the ids of every kind after it.
2. Add its text in `NotificationTexts.For`.
3. Add its channel in `NotificationPlanner.ChannelOf`, its rank in `Priority`, and its input in `NotificationInputs` and `FromSave`.
4. Add a test in `NotificationPlannerTests`.
