# Architecture Map (always read this)

**Scope:** Structural map of the codebase — scenes, layers, data flow, init order, what not to touch.

## Scene & boot flow

```
SplashScene  ──►  LoadingScreen (overlay scene)  ──►  GameScene
  auth + cloud      SceneLoader transition             single gameplay scene
  reconciliation                                       contains ECS SubScene (TestSubScene)
```

1. `SplashScene`: persistent singletons awake (`SaveManager`, `SettingsService`); UGS auth + cloud save reconciliation; then `SceneLoader.GoTo("GameScene")`. `PremiumShopService` and `IAPService` are not scene-placed — they are created at startup by `PremiumServicesBootstrap` (`[RuntimeInitializeOnLoadMethod]`, `Assets/Scripts/Bootstrap/`).
2. `GameScene`: ECS world spawns; SubScene bakes `Assets/Scripts/Authoring/*` into entities; `ECSLoadBridge` polls for ECS singletons (5s world timeout + 10s entity timeout), then applies `SaveData` → ECS and calls `GridSaveService.Instance.LoadGrid()`. Only after `ECSLoadBridge.IsLoaded == true` is gameplay state valid.
3. There is no MainMenu scene. All menus (shop, settings, prestige, etc.) are panels inside the single `Assets/UI/GameHUD.uxml`.

## Three layers

### ECS simulation (`Assets/Scripts/Systems/`, all in `SimulationSystemGroup`)

| System | Role |
|---|---|
| `ProductionSystem.cs` | Per-building craft loop: top up the creation buffer (`CraftStagingSlot`, up to one craft's recipe quantities) from the local `BuildingInputSlot` buffer and start when it holds the whole recipe (`CraftStaging`; both empty falls back to global inventory), advance `Progress += dt × BuildingData.ProductionSpeed`, consume inputs, deposit to `BuildingOutputSlot`. Burst-compiled `ISystem`. |
| `CollectorSystem.cs` | Field harvesters: produce items at fixed rate, no inputs. |
| `ConveyorSystem.cs` | Moves items building output slot → adjacent input slot, respecting ports/direction. **Belt density:** each segment carries a `ConveyorItem` buffer (front first, `Systems/ConveyorItems.cs`); a tile holds `BeltSettings.ItemsPerTile` items (game_config `belt_items_per_tile`, default 2, baked by `PlayerInventoryAuthoring`) and items keep `1 / ItemsPerTile` tiles apart along the whole chain, so a belt carries speed x ItemsPerTile items/s and a blocked belt packs side by side. Segments move tails first and a handing-off item carries its overshoot (`BeltMotion`); either shortcut makes belts run slow. Input hand-off rules live in `Components/InputAcceptance.cs`: the input cap is **per item type**, a set recipe refuses items it does not use, an item the recipe uses that reaches a full input is sold at the surplus price (full-input autosell), and a mixed belt whose front item is jamming a needed item sells that front item too (#200, #312; `Services/SurplusSale.cs`, which also sells inputs a newly set recipe no longer uses). A belt's tail feeds any adjacent input port facing it, ranked by `TailInputPriority` (the input its `ExitDir` points at first, Maxwell's Demon last, #275; `ConveyorSystem.TryPickInput`). `ConveyorVisualizer` draws the tail exiting toward the input it actually delivers to: `ConveyorSystem` logs each deposit's direction in `TailDeliveryLog` (runtime-only, keyed by cell; first delivery sets it, a change needs 3 in a row so a briefly full input doesn't flicker), and before the first delivery it falls back to the same ranking (`Grid/TailDelivery.cs`, #223). The ranking alone drew a belt into an input ahead whose recipe doesn't use the item while items went to a side input. |
| Building → belt feed (in `ConveyorSystem` pass 4) | A building's output port feeds the belt tile in front of it when that tile is a chain head, or when a belt runs through it (a merge at a harvester's exit, #206). On a merge cell the building is one more source in the `MergeCursor` round robin (pass 3 marks its turn, pass 4 pulls, `ConveyorSystem.NextFeedItem` respects Filters). A belt that only ENDS on the tile takes nothing, and streams never take this path (banks use side drop). `PortArrowRules` matches. Offline, `IdleGraphAnalyzer` gets output ports through `getOutputPorts` (`GridSaveService.OutputPorts`) and routes such a producer from that cell. While a belt is traced, `ConveyorTopology.PreviewSeams` shows the "not connected" seams it would leave before ✓ (#208). |
| `Grid/BuildingProgressBars.cs` | World-space progress bars over producing buildings (#211): harvesters follow `CollectorData.Timer`, crafters with a recipe their craft (`ProgressBarRules`). Reads ECS each `LateUpdate` and draws all bars as two `Graphics.RenderMeshInstanced` batches (background, fill), camera-facing, lifted by footprint. Added at runtime by `BuildingVisualizer.Awake` (no scene wiring); Settings toggle `toggle-progress-bars` → `SettingsData.showProgressBars` (default on). |
| `FilterSystem.cs` | Filter buildings (#321): moves input items to the output buffer only when some side takes them (`Gameplay/PortFilterRules.cs`); `ConveyorSystem` then lets each output belt pull only its own items. Offline, `IdleGraphAnalyzer` treats Filters as see-through. |
| Belt splits (in `ConveyorSystem`) | A belt tile with a `BeltSplit` (output mask + weight 1-5 per side, set by press-and-hold → `BeltSplitCard`) hands each item to one of 2-3 sides. `PlanSplitExits` gives every item on the tile its exit by smooth weighted round robin (`Gameplay/BeltSplitRules.Pick`) so it curves toward its branch (`ConveyorItem.OutEdge`); at the edge it re-picks if that branch is full, and waits if all are. A side can also face a building's input port (a split right in front of an input): it counts as an output, takes its turn straight into the input when `DecideDeposit` accepts the item, and passes the turn on while the input is full (`SplitInputAt`; offline, `IdleGraphAnalyzer.Route` gives that side's share to the building). Topology counts split outputs as inbounds (`ConveyorTopology.Compute` `splitMasks`), so branches aren't chain heads. Saved as `GridSaveData.splits` plus a chain per branch. Offline, `IdleGraphAnalyzer` shares each chain's flow at every split by weight. Replaced the Belt Splitter buildings (2026-11-24; `SaveSystem/SplitterMigration` converts old ones on load). |
| Overpasses (in `ConveyorSystem`) | A ramp-up belt tile with a `BeltBridge` (`Exit` = ramp-down tile, `Length` = crossed + 1 tiles) is one segment spanning the tiles it crosses; `Len`/`FrontLimitInto`/`RoomInto`/`CarryInto` convert progress and spacing between segments of different lengths, so the span runs at belt speed and rate. `ConveyorTopology.Compute` `bridges`: a ramp-up outputs only to its ramp-down, which takes it in on the span side; neither ramp links to a belt on its span side (that runs under). Tiles under a span are `GridOccupancy.IsUnderOverpass` (belts yes, buildings no). Laid by the Up button while tracing (`ConveyorTrace.TryAdd(cell, raised)`, `Gameplay/OverpassRules`), unlocked by the `overpasses` research (4 tiles; `overpasses_ii` 8). Saved with no extra field: the chain lists the two ramps side by side, and `ConveyorPlacer.PlaceConveyorChain` makes any non-adjacent pair a span. |
| `StreamFlowSystem.cs` | Stream worlds only (Chemistry, `StreamSegment` belts): shares each Spring's flow among the buildings beside its stream, upstream first, writing `StreamStatus` (ProductionSystem and CollectorSystem multiply by its `Ratio`) and the `StreamGridState` HUD totals. `ConveyorSystem` has stream-only passes: bank side pickup (recipe inputs only), mid-tile side drop, dry channels stand still, an open mouth sells as surplus. See `chemistry-biology.md` "Streams". Streams only flow away from their source (#543): on confirm, `ConveyorPlacer.OrientStreamRun` keeps a drawn run whose first cell a Spring feeds (or that extends a stream's mouth), reverses it when only its last cell is fed, and refuses it otherwise (`StreamRules.NoSourceMessage`); a lone tile never faces back into its Spring. Player placement only, never on load. At a stream's head ConveyorSystem pass 4 pulls from the Spring only; every other building beside the head drops from the side (`StreamSideDrop`). |
| `PowerGridSystem.cs` | Proximity power grid (single shared eV pool): connects consumers within a generator's `link_radius_tiles` (range-limited connections, relayed through **Power Relay** buildings), computes global supply/draw/throttle, writes `PowerStatus` + `PowerGridState`. Runs `[UpdateBefore]` `ProductionSystem`, which throttles craft progress by `PowerStatus.ThrottleRatio`. |
| `EntropySinkSystem.cs` | Sink building consumes items → grants entropy (base currency). Also logs each batch to the `DemonDelivery` buffer (`DemonDeliveryLog` entity) for the world delivery tasks. |
| `FactoryClockSystem.cs` | Runs first in the group: sets the `FactoryClock.Rate` singleton to 2 while a speed burst (`speedBoostExpiryUtc`: shop Speed-Ups, Production Surge ad) runs, else 1. `ProductionSystem`, `CollectorSystem` and `ConveyorSystem` multiply delta time by it, so crafting, harvesting and belts all run 2x together; `ConveyorVisualizer` scrolls the belt lattice with it. Research timers, the craft queue, field cooldowns and real-time countdowns stay on wall time. Income credited while it runs is divided back out of `AutomationIncome.Unboosted`. |
| `NetWorthSystem.cs` | Aggregates net worth: inventory + items waiting in building inputs/staging/outputs (Demon price, Demon itself excluded; also written to `StoredItemValue`) + entropy held + `TotalEntropySpent` (price paid) + `TotalEntropyDiscounted` (list price minus price paid, so purchases count at full value) + `BaseNetWorth`; drives prestige wall. |
| `PrestigeSystem.cs` | Wall detection + prestige execution: currency formula, run reset, destroys buildings + every belt segment (and its item) and empties the kept Demon, since the default world outlives the scene reload; service resets, forced save. |
| `TutorialSystem.cs` | Advances `TutorialStateData` through `TutorialFlowSO.Current.steps` conditions. |
| `ProductionAchievementBridge.cs` | Forwards ECS production events to `AchievementService.Notify*()`. |

| `ResearchService` | `Assets/Scripts/Services/` | Research purchase: prereqs + `EntropyWallet.TrySpend` (`ResearchService.Purchase`) via ECS; fires `OnResearchUnlocked`. |

Deadlines later than the current period's end (written from a fast clock) are clamped without a reset. Every load/check/reset decision is logged under `[Achievements]` at Info level for on-device diagnosis. **Daily counts from the start; the rest waits for the first prestige (2026-11-20):** `Evaluate()` skips Weekly/Monthly/Progression achievements while `tutorial.hasCompletedFirstRun` is false (`CategoryUnlocked`), and no unlock toast or reminder dot shows while the tutorial runs. ### UI (`Assets/Scripts/UI/`, UI Toolkit)

`HUDController` (on a GameObject in GameScene with a `UIDocument` → `GameHUD.uxml`) owns everything; sub-controllers are **MonoBehaviour components on the same GameObject**, fetched via `GetComponent<>()` (`HUDController.cs:106-111`). See `ui-toolkit.md` before any UI work.

The Research panel shows `ResearchTreeView` (a code-built `VisualElement` inserted after `research-list`; #337), or the card list; a header button switches between them (`PlayerPrefs` `research_view_mode`, tree by default). Both work during the tutorial: the tree opens on and selects the research the current step asks for (`HUDController.TutorialResearchTargetId`), and the list still hides research beyond the immediate frontier. The tree reuses `HUDController.BuildResearchCard` for the selected node, so Start, timer and crystal skip behave the same in both views. Layout: `ResearchSO.treeX`/`treeY` from the research tree editor, else `ResearchTreeView.Layout` (blocks left to right, prerequisite-depth columns). Painter2D colours go through `.linear` (the project renders in linear colour space).

## Data flow

```
Assets/Data/game_data.json ──(Editor menu: MobileIdleBuilder > Import Game Data)──► SO assets
        SOs ──(Authoring bakers in SubScene)──► ECS components/entities
SaveData (save.json) ◄──ECSLoadBridge.FlushToSave()/ApplyLoadedSave()──► ECS singletons
        SaveData ◄──SaveManager──► local file + UGS cloud
```

## Init order rules (race conditions are a recurring bug source here)

- Singletons override `Awake()` MUST call `base.Awake()` (CLAUDE.md rule).
- Never read/write ECS singletons from a MonoBehaviour before `ECSLoadBridge.IsLoaded` is true. The bridge's polling coroutine is the only sanctioned wait; copy how `TutorialOverlayController` guards its `Update()` on `ECSLoadBridge.IsLoaded`.
- Sub-controllers receive ECS access via `SetECSContext(EntityManager)` called by `HUDController` after the bridge loads — do not create your own timing.

## Time

Anything a player waits on (research timers, field cooldowns, speed boosts, offline earnings via the background timestamp, daily/weekly/achievement resets, ad caps) reads `GameClock.UtcNow` (`Assets/Scripts/Services/GameClock.cs`), never `DateTime.UtcNow`. Release builds read the wall clock; editor/dev builds let the AI playtest harness freeze and fast-forward it (`Playtests/README.md`, "Time"). Stays on the wall clock: `SaveData.lastSaved` (cold-boot offline earnings + cloud reconcile), the idle snapshot stamp, auth policy, telemetry.
 **PvE tournaments are the exception:** the server decides every tournament time (Cloud Code clock); the client shows its run timer and prestige lock from `TournamentService.Now` = the dev console debug time, else `ServerClock.UtcNow`, else the wall clock.

## Key ECS singletons (components in `Assets/Scripts/Components/`)

| Singleton | Fields that matter | Written by |
|---|---|---|
| `PlayerProgressData` | `BaseCurrency` (entropy), `TotalEntropySpent`, `TotalEntropyDiscounted` (saved), `StoredItemValue` (derived), `NetWorth` (double, #284), `CurrentTier`, `PrestigeWallValue/Available/Requested` | NetWorthSystem, PrestigeSystem, ECSLoadBridge, UI |
| `PrestigeData` | `RunCount`, `PrestigeCurrency(+Spent)`, `SpeedMultiplier`, `OutputMultiplier`, `CostReduction` | ECSLoadBridge, PrestigeSystem, PrestigeShopSubController |
| `TutorialStateData` | `IsActive`, `CurrentStepIndex`, `FirstRunComplete` | TutorialSystem, ECSLoadBridge |
| `InventorySlot` buffer on the `PlayerInventoryTag` entity | global player inventory (`ItemID`, `Quantity`) | ProductionSystem, ECSLoadBridge, ManualCraftService |

`PrestigeData.SpeedMultiplier`/`OutputMultiplier` (Assembly Line / Quantum Yield) are read live by `ProductionSystem` and `CollectorSystem` (alongside `GlobalProductionBonus`) and by the idle snapshot. They hold the pure prestige values: `ECSLoadBridge` recomputes them from the purchased upgrade levels on load and never composes the timed speed burst into them (the burst runs the factory clock instead: `FactoryClock`, below). `CostReduction` affects building prices (`EntropyWallet.ReducedCost`, used by `HUDController` and `DemolishRefund`).

## Do NOT edit

- `docs/gameplay-loop.html`, `gameplay-loop.js`, `gameplay-loop.css`, `docs/gameplay_loop_data.js` — human-only reference site; it may lag behind code, so do NOT treat it as authoritative or look balance values up there. For authoritative item/recipe/building/cost values use `Assets/Data/game_data.json` (the single source of truth). Never load the HTML.
- Generated `.asset` files under `Assets/Data/` and `Assets/Resources/` — regenerate by editing `game_data.json` and re-running the importer (see `data-pipeline.md`).
- Any UXML other than `Assets/UI/GameHUD.uxml`, `SplashScreen.uxml`, `LoadingScreen.uxml` without first grepping that it is actually loaded at runtime (CLAUDE.md rule).
- `Assets/GoogleSignIn/` native plugin code.
