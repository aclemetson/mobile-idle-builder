# UI Toolkit: GameHUD, Controllers, Panels

**Scope:** How the runtime UI is structured and how to add a panel without falling into the known traps. Read before any UI/UXML/USS work.

> Verified against: `deea0a4`, 2026-06-11; back-button rule 2026-10-31 (#205); Recipes tab groups by output item 2026-11-07 (#336); Entropy Surge offer 2026-11-11; building edit mode 2026-11-17; conveyor tracing + `TapGesture` 2026-11-17; Statistics stored-value row 2026-11-19; landscape side sheets + PanelDock 2026-11-19; player name card 2026-11-23; PvE tournaments (TournamentService) 2026-11-23. If code contradicts this doc, trust the code and update this doc.

## The one true document

`Assets/UI/GameHUD.uxml` is the ONLY gameplay HUD loaded at runtime (via `UIDocument` on the HUD GameObject in GameScene). `SplashScreen.uxml` and `LoadingScreen.uxml` cover their own scenes (the splash also hosts the maintenance and update-prompt panels; see `feature-flags.md`). **Any other UXML file is suspect — grep that it is loaded before editing it** (CLAUDE.md rule; standalone modal UXMLs have burned us before).

### Verified element inventory in GameHUD.uxml (by `name=`)

`top-bar` (:21), `left-drawer` (:42), `recipe-panel` (:73), `buildings-panel` (:84), `codex-panel` (:96), `research-panel` (:107), `upgrades-panel` (:118 — this is the prestige shop), `achievements-panel` (:132), `prestige-panel` (:152), `sites-panel` (Quantum Domains — multi-grids site switcher), `pvp-panel` (the Tournament panel: `TournamentPanelController`, drawer button `btn-pvp` "Tournament"), `shop-panel` (:191 — premium/crystal shop), `settings-panel` (:210), `placement-overlay`/`placement-bar` (:249) + `placement-confirm-popup` (world-anchored ✓/✕), `conveyor-overlay` (:260), `deconstruct-overlay` (:269), `building-inspector-panel` (:295), `demon-panel` (:306), `idle-return-modal` (:378).

Slide-in panels share `class="slide-panel hidden"` — visibility is toggled by adding/removing `hidden`.

## Controller pattern

- `Assets/Scripts/UI/HUDController.cs` is the orchestrator (large file, ~1300 lines).
- Sub-controllers are **MonoBehaviour components on the SAME GameObject as HUDController**, marked `[RequireComponent(typeof(HUDController))]`, and fetched with `GetComponent<>()` in `HUDController` (`HUDController.cs:106-111`). They are NOT constructed in code and NOT separate scene objects.
  - **Trap:** a new sub-controller class does nothing until the component is added to the HUD GameObject in `GameScene.unity`. `[RequireComponent]` does not retro-add it to an existing scene object — this is a manual Unity Editor step; flag it to the user in your final report.
- Lifecycle calls made by HUDController on each sub-controller: `Init(VisualElement root, HUDController hud)` (query elements by name, e.g., `root.Q("upgrades-panel")`) then `SetECSContext(EntityManager em)` once ECS is ready, then `Refresh()` when the panel opens. Copy `Assets/Scripts/UI/PrestigeShopSubController.cs` — it is the cleanest reference (panel + currency label + ScrollView list rebuilt in `Refresh()`).
- `SitesSubController.cs` is a second clean reference (sites-panel): list rebuilt in `Refresh()`, a pure `ClassifyRow(isActive, isUnlocked, canAfford)` helper drives each row's action (Active/Travel/Unlock/Locked), and the Travel handler calls `HUDController.CancelActiveModes()` before `SiteService.SwitchTo` so placement overlays clear before the grid swaps.
- Drawer nav buttons are wired in HUDController around `HUDController.cs:454-491` (`root.Q<Button>("btn-recipes").clicked += () => TryOpenPanel(OpenRecipePanel);`). New panels add a button + `OpenXPanel` method here.
- Building rows/list items are built **in C#** (`new VisualElement()` + `AddToClassList`), not via UXML templates, in sub-controllers — follow that style.

## Building inspector: no layout bounce

`HUDBuildingInspectorSubController` clears and rebuilds `inspector-static` / `inspector-recipes` / `inspector-upgrades` every 0.5s. Anything whose row count changed between rebuilds shifted the scrolls below and moved buttons out from under the finger (0.4 checklist item 21). Rules for this panel:

- **Layout (2026-11-14):** `inspector-static` pins only the progress bar, one `.inspector-buffers` line (`IN [chips] [empty]  OUT [chips] [empty]`, built by `MakeBufferGroup` / `MakeItemChip` with the item's icon sprite, `GlyphIcon.Kind.Empty` icon buttons that show the `EmptiedMessage` banner), and a `⚡` row only when the building is unpowered or browned out. Everything else (Active, Cell, collector rate, Produces + value/surplus lines, escape bonus, power draw/status) goes into `inspector-info`, inside the floating `inspector-info-card` toggled by `btn-inspector-info` (`GlyphIcon.Kind.Info`, left of the close button; tapping the card closes it too). The card overlays the recipe/upgrade scrolls so opening it never moves them. It must stay the panel's LAST child (UI Toolkit draws later siblings on top; earlier, the recipe buttons painted over it), and its `top` is set from the header's measured bottom (`PositionInfoCard`, on the header's GeometryChangedEvent); `_infoOpen` survives rebuilds and resets on hide / a new building. Power-source cards (`output-selector--power`) keep their rows pinned and hide the (i).
- **Reserve, don't add/remove.** Buffer chips are one per recipe-expected item (`StableBufferRows`, ×0 when absent, dimmed); the Empty buttons are always present and `SetEnabled(false)` when empty; the input section shows whenever the building *can* hold inputs (`ShowInputBufferSection`). Maxed upgrade rows keep their description + footer with a disabled "Maxed" button (`AddUpgradeRow`). Manager rows are one same-shaped row per hired manager in catalogue order; assign/unassign only flips the button text.
- **Backstop:** `inspector-static` gets a `min-height` high-water mark per inspected entity (`OnStaticGeometryChanged`), reset on entity change / hide.
- All inspector buttons route through `ListTapRouter` (not `.clicked`): the ScrollView eats a Button's own Clickable on touch, and the 0.5s rebuild would drop a held press. The rebuild also waits while `ListTapRouter.GestureInProgress` (finger down, capped at 1s), since replacing or disabling the button mid-press lost the tap.
- Destructive actions ask first via `ConfirmPrompt.Show(title, message, confirmLabel, onConfirm, onCancel)` (static; `confirm-prompt` in `GameHUD.uxml`, initialised by `HUDController`). It sets `UIInputBlocker.SetModal` while open; world controllers also skip their tap handling while `ConfirmPrompt.IsOpen` so the target stays highlighted. Removing a building asks; removing a conveyor tile does not (belts are free to replace).
- Blocked-action feedback (`InventoryPopupController.NotifyWarning`, so `ToastService` and the tutorial gates) shows in the HUD notification banner with the `warning` style, not as world text over the player anchor, which could spawn off-screen (#238).
- A `<ui:Instance>` in `GameHUD.uxml` that holds an absolutely positioned overlay (dialogue, notification banner, tooltip) needs `picking-mode="Ignore"` and `style="position: absolute; left: 0; right: 0; top: 0; bottom: 0;"`. Without it the TemplateContainer is laid out in the root's flex column below the grid area, so its overlay's `top`/`left` start from the bottom edge: the notification banner sat off screen and only flashed into view while sliding (#238). `HudOverlayInstanceTests` checks this.

## Tutorial sell gate (Maxwell's Demon)

During the hand-crafting phase, which runs up to the last tutorial step that advances on `InventoryZero`, the Demon panel only takes what the current step asks for. `TutorialSellPolicy.CanSell` lets a sell step sell its condition items and `demonHighlightItemIds`, and lets any other step in the phase sell nothing. After that phase, or outside the tutorial, everything sells. Belt deliveries never go through the policy.

How the panel enforces it (`MaxwellsDemonController`):
- Rows that can't be sold get `demon-item--locked`: they are dimmed and show no value.
- Tapping or dragging a locked row posts `TutorialSellPolicy.BlockedMessage`.
- `CommitDeposit` and `DepositAll` skip locked items, and Deposit All is disabled when nothing can be sold.

Why the gate exists: selling quarks on a craft step, where collection is paused, used to strand the player. Saves already stuck that way are recovered by `TutorialCraftRescue`. It works out the raw inputs a `blockCollection` + `InventoryMin` step still lacks, counting held items plus queued crafts and following recipes, and returns the field type to reopen.
- `ManualFieldCollector.IsCollectionAllowed` honours that field type.
- `TutorialOverlayController.RefreshCraftRescue` un-dims those fields and shows `RescueMessage` once.

Covered by `TutorialSellPolicyTests`.

## Tutorial hint banner (minimizable)

`tutorial-hint-banner` (bottom of `GameHUD.uxml`) is owned by `HUDBannerController` (`ShowTutorialHint` / `HideTutorialHint`, called via `HUDController` by `TutorialOverlayController`). Its minimize button (`tutorial-hint-banner__minimize`, icon is a drawn bar, not a glyph) collapses it to the `tutorial-hint-restore` "Show hint" pill (bottom-right). Minimized state sticks while the same text is re-shown, but a hint with **different text re-expands** so a new step's guidance is never hidden; hiding the hint hides the pill too. `HUDController.RefreshBannerClearance` runs every frame and calls `HUDBannerController.SetMenuOpen(drawerOpen || any slide panel visible)`, which collapses the banner to the pill (its full-width bottom bar hid the drawer's and the Builder sheet's Place buttons) and restores it when everything closes, unless the player had minimized it. Keep it per-frame, not per open path: an explicit call in one open method missed the Builder sheet, which opens after the drawer closes. Under the hint text, `tutorial-hint-banner__progress` shows live have/need counts for `InventoryMin` steps ("Up Quark 2/4, Down Quark 1/2, Electron 0/2"): `TutorialOverlayController.RefreshHintProgress` (every 0.2s) formats it with the pure `TutorialHintProgress.Format` and pushes it through `HUDBannerController.SetTutorialHintProgress`, which never re-expands a minimized hint (#260). Covered by `TutorialHintMinimizeTests` (runs against the real UXML) and `TutorialHintProgressTests`.

## Landscape and panel docking (2026-11-19)

- **Scale:** `UIScaler.ScaleForScreen` scales from the screen's SHORT side and re-applies when the screen size changes, so the HUD is 540 units on its short side in either orientation (by width, a landscape launch gave a 540x250 HUD). `SplashScreenController` uses the same call.
- **Landscape:** `HUDController.QueryElements` toggles `hud--landscape` on `#root` when it is wider than tall (`IsLandscape`). In `GameHUD.uss` that turns every `.slide-panel` into a right-hand side sheet under the top bar (`left: 40%`; `#research-panel` 24%), and lays the research tree out side by side: tree left, `.rt-detail` card right.
- **Docking:** `HUDController.RefreshPanelDocking` (per frame, from `RefreshBannerClearance`) moves the `tutorial-hint-restore` pill and the `dialogue-box` onto the map beside an open slide panel: above it in portrait, left of it in landscape. `PanelDock.For` picks the strip, and the piece keeps its USS place when the strip is too small. The docked dialogue gets `dialogue-box--docked` (smaller text). Before this the pill sat on the research Start and craft-queue Cancel buttons. Covered by `PanelDockTests`.
- **Research tree pan:** `ResearchTreeView.ClampAxis` pins content that fits to the top/left edge and stops larger content at the viewport edges. Centring a node in a two-row tree had left a third of the viewport empty above it.
- **Research tree lines:** columns are 270 apart and rows 112 (48px gutters). `ResearchTreeView.Route` draws a line between neighbouring columns as a curve. A line that skips columns (most cross-block prerequisites) becomes right-angled segments: it runs through the column gaps and the gutter between rows, each on its own track. A straight line had run under the nodes in between and made them look like prerequisites. `ResearchTreeLayoutTests` checks that no line passes under another node and that lines from different sources never overlap. `docs/research-tree.html` uses the same COLW/ROWH.
- The research Tree/List toggle (`.research-view-btn`) and the card's Start/Skip buttons are `flex-shrink: 0` with a 44px minimum height. The header row had squeezed the toggle to a sliver.
- `.notification-banner` starts at `left: 56px` so it no longer covers the drawer handle (≡).

## Notification banner (top of screen)

`notification-banner` (`Components/NotificationBanner.uxml`, owned by `HUDBannerController`) starts at the same `--top-bar-height` as the mode bars and the inspector, so it needs clearance from both. While it is up, every `.placement-overlay` (placement, conveyor, deconstruct) gets `padding-top` = banner height + gap, following a wrapped message's real height (`ApplyNotificationClearance`), so the bar moves down rather than being covered. The inspector is deliberately not pushed: its upgrade buttons raise this banner, and moving them breaks the no-bounce rule above, so while it is open the banner sits over `top-bar` instead (`RefreshNotificationClearance`, per frame from `RefreshBannerClearance`). A new top-anchored mode bar should reuse `.placement-overlay` to get the push. Swiping sideways or up past `BannerSwipe.DismissDistance` dismisses it; a shorter drag slides it back and restarts the auto-hide timer, which pauses while a finger is down. It carries `blocks-world-input` so a swipe never pans the map. Covered by `NotificationBannerTests`.

**Actionable banners (2026-11-15):** `ShowNotification(icon, msg, modifier, onTap, onAccept)`. A press that moves under `BannerSwipe.TapSlop` runs `onTap`; `onAccept` shows the `notification-banner__accept` check button (`GlyphIcon.Kind.Check`), whose press is excluded from the swipe capture so its click is not swallowed. Either action dismisses the banner. Actionable banners stay up `actionableNotificationDuration` (5 s), and a later notification clears both actions. Achievements use it through `HUDController.ShowAchievementNotification`: a tap opens the menu on that achievement's tab, and the check button claims the reward. Before the first prestige the menu is locked, so the banner is a plain notice.

## Power readout & coverage (proximity power feature)

- **Top bar width:** with Prestige showing there is about 35px spare on a 540px-wide panel, so amounts use `NumberFormat.Compact` and new items need another home. `TopBarLayoutTests` guards the readout staying out of it.
- **Power strip** (`power-status` > `power-label`, directly under `top-bar`; hidden until `ShowsPowerStrip`: a generator exists or a building waits for one): `HUDStatusBarController.RefreshPowerLabel` reads the `PowerGridState` singleton and shows `⚡ draw / supply eV`. On a brownout (`Draw > Supply`) or any unpowered consumer it prefixes `⚠`, appends `(N unpowered)`, and toggles the `power-brownout` USS class (`GameHUD.uss`, red via `--color-danger`). The status bar's power query is `PowerGridState` (not `PowerNodeData`).

- **Coverage tiles**: `GridRenderer.ShowPowerCoverage(x,y,w,h,radius)` / `ClearPowerCoverage()` tint covered cells blue using the same `SetTileHighlight` layer as the placement ghost (cleared automatically by `HideGhost`). ## Camera controls (orbit rig)

`CameraController` (`Assets/Scripts/Camera/CameraController.cs`, on Main Camera) orbits a ground pivot rather than holding a fixed isometric angle. Authoritative state is `_pivot` (focal point on the Y=0 plane), `_yaw`, `_pitch`, and `_distance`; the transform is rederived every `LateUpdate` via `ApplyRig()` so the camera always looks at the pivot. The serialized `offset` only seeds the initial yaw/pitch/distance (default `(0,8,-6)` → the old isometric view). `OrbitOffset(yaw, pitch, distance)` is a pure static helper (edit-mode tested in `CameraControllerTests`).

- **Pan** — single-finger swipe (mobile) / left-drag (desktop) moves `_pivot` along the ground via `ScreenToGround`, clamped to grid bounds by `ClampPivot`. `HandleSwipePan` skips when ≥2 touches are down.
- **Zoom** — two-finger pinch distance and scroll wheel adjust FOV, clamped `minFOV..maxFOV` (limited zoom; no distance change).
- **Rotate** — two-finger swipe (the fingers' centroid delta, applied *simultaneously* with pinch zoom) or middle-mouse drag (`HandleMouseOrbit`). Horizontal → yaw, vertical → pitch; pitch clamped `minPitch (10°, near-horizon) .. maxPitch (90°, straight down)`. Manual rotate cancels any active tutorial pan.
- **Lock** — rotation and pan are gated by `_panLocked` (`SetPanLocked`). Only the Maxwell's Demon minigame locks the camera; **destroy and conveyor modes do NOT lock it**, so pan/zoom/rotate all work there (rotation is two-finger / middle-mouse and never collides with single-finger conveyor painting).
- **Tutorial** — `PanTo(worldPos)` / `ResumeFollow()` lerp `_pivot` toward the target (API-compatible with the old `IsometricCameraFollow`).

## Building placement (tap-to-position + confirm popup)

`BuildingPlacementController` does NOT place on press and does NOT lock the camera. Flow (editor mouse + mobile touch, one code path via `InputUtils`):

1. **Press-drag pans** the map (camera stays unlocked during placement). Tap vs. pan/zoom is `TapGesture` (see "World taps" below): a drag, a pinch, or a touch that stops a gliding map never places.
2. A **stationary tap sets a candidate cell** (`SetCandidate`), locks the ghost there (`_hasCandidate` skips the desktop hover-follow), and raises `OnCandidateChanged(true)`. Tapping another cell repositions; Rotate/Flip re-draw the ghost at the candidate.
3. A **world-anchored confirm popup** (`placement-confirm-popup` in `GameHUD.uxml`, ✕ `btn-cancel-candidate` / ↻ `btn-rotate-candidate` / ✓ `btn-confirm-place`) floats above the candidate. `HUDController.UpdatePlacementConfirmPopup` repositions it every frame via `RuntimePanelUtils.CameraTransformWorldToPanel(panel, CandidateWorldPosition, Camera.main)`, disables ✓ when `CandidateValid` is false, and hides it on `OnCandidateChanged(false)` / placement end. ✓ → `ConfirmCandidate()` (runs the field output-selector if needed, else `ConfirmPlacement`); ✕ / Esc → `ClearCandidate()`; ↻ → `placementController.Rotate()` (same call as the bottom-bar `btn-rotate-output` and the R key). The ↻ button is shown by `OnCandidateChanged` only when `placementController.CanRotate` is true; the per-frame re-anchor + ✓-validity refresh already pick up the new footprint after a rotate. Flip stays on the bottom `placement-bar` (`btn-flip-building`), not the popup.

**Why ✓ is disabled:** `IsCellValidForPending` is `BlockAt(x, y) == PlacementBlock.None`. `BlockAt` returns the first reason a cell fails (`OffGrid`, `Occupied`, `NeedsField`, `WrongField`, `OnField`, and in edit mode `FieldLacksRecipe`), and `SetCandidate` shows `BlockMessage(...)` through `InventoryPopupController.NotifyWarning` on every tap of an invalid cell, so a disabled ✓ always comes with a reason (#258). Messages must fit the one-line banner (`PlacementBlockMessageTests` caps them at 56 characters). A new placement rule adds a `PlacementBlock` value and a message, not a bare `return false`.

**Gotcha (cost a debug cycle):** `BuildingPlacementController.IsPointerOverPlacementUI` (assigned by `HUDController`) must hit-test the **`placement-bar`** strip and the popup — NOT the `placement-overlay` container, which is full-screen/transparent so the world shows through. Hit-testing the overlay makes *every* tap read as "over UI", so no candidate is ever set and the popup never appears. Use `ScreenPointInElement` (`RuntimePanelUtils.ScreenToPanel` + `worldBound.Contains`).

## Building edit mode (press and hold a placed building)

Holding still on a placed building puts it back into placement mode so it can be moved, turned or flipped without being destroyed. The entity is kept, so its items, craft progress, recipe, upgrades, manager and Filter rules go with it, and moving is free.

- **Gesture:** `PlayerInputRouter` starts a hold on press when `BuildingInspectorController.TryGetEditableBuildingAt` finds a building (not over UI, no mode active, no tutorial `buildingInteractionGate`, never Maxwell's Demon, whose baked cell is never restored from save). Timing is `LongPress`: the `HoldProgressRing` (Painter2D, created from code on the HUD root, picking ignored) appears at `RingDelay` and fills until `HoldSeconds`, then `BuildingPlacementController.BeginEdit` runs. The hold is cancelled as soon as the press can't be a tap (`TapGesture.IsDisqualified`: it moved past the slop, a second finger joined, or it stopped a glide). A release before `HoldSeconds` is an ordinary tap (opens the inspector); the release after edit mode starts is swallowed.
- **Edit flow:** `BeginEdit` hides the building (`BuildingVisualizer.SetBuildingHidden`, which also hides its port arrows and holes) and sets the candidate on its own cell. In edit mode `BlockAt` treats the building's old footprint as free (`IsOccupiedByOther`), and a moved harvester must land on a field that still yields its recipe (`PlacementBlock.FieldLacksRecipe`). ✓ calls `BuildingPlacer.MoveBuilding` (occupancy swap) → `BuildingMove.Apply` (anchor, footprint, ports, legacy output side, Filter rule facings via `RemapFacing`, splitter turn) and re-keys any manager (`ManagerService.MoveBuilding`); no `OnBuildingPlaced`, so nothing is charged. Cancel restores the building where it was.
- **Remove:** `btn-remove-building` in `placement-bar` (visible only while `IsEditing`) calls `RequestRemoveEditedBuilding` → `DeconstructController.ConfirmRemove`, the same "Remove {name}?" prompt and refund as deconstruct mode. Deconstruct mode stays for removing several buildings in a row. Placement input pauses while `ConfirmPrompt.IsOpen`.

## Conveyor placement (trace a belt)

`ConveyorPlacementController` Create mode is a `ConveyorTrace` (pure, `Grid/ConveyorTrace.cs`): tap a start, then each next point; ✓ places the whole belt as one chain and clears the trace (the next tap starts a new belt; Done exits).
- Between consecutive points the belt is **auto-routed** like the old start/end placement: straight when aligned, else an L in the segment's bend, else a detour (`ConveyorPathfinder`, cheaper of L and route wins, router extra cost from `MakeExtraCost`). Cells already on the trace are blocked, so a belt never crosses itself. Two taps and ✓ give the same belt as before, which the tutorial's "tap here, then there" steps rely on.
- A point on an existing belt (not the start) **merges** and ends the trace; starting on an existing belt is allowed. Tapping the start again while it is the only point makes a single belt (Rotate turns it).
- Every added point is checked against `ConveyorTopology.CanPlace` through `ConveyorPlacer.RejectReason`, so a fork or an overfull merge is refused on the tap with a reason (`ConveyorPlacer.PlayerReason`) instead of ✓ silently doing nothing. `PlaceConveyorChain` returns `bool` and a refusal too.
- Bar (`conveyor-bar`, refreshed by `HUDController.UpdateConveyorBar` on `OnTraceChanged`): Bend `btn-conveyor-rotate` (last segment only) and Place `btn-conveyor-confirm` once a belt can be placed; Undo `btn-conveyor-cancel-candidate` (`GlyphIcon.Kind.Undo`, removes the last point) and New once a start is set. The label comes from `HUDController.ConveyorBarLabel`. Refusal lines live in `BeltFeedback` (≤ 45 chars, no ✓ glyph: Android's font lacks it).

## World taps (`TapGesture`)

Every world-tap consumer (`PlayerInputRouter`, `BuildingPlacementController`, `ConveyorPlacementController`, `DeconstructController`) feeds a `TapGesture` through `InputUtils.PumpTap` and acts only on its result, so they agree on what a tap is. A press is **not** a tap when it began over UI, moved farther than the slop from its press point (the farthest distance, not the summed path, so jitter doesn't add up), had a second finger at any point (pinch/rotate/tilt: only the primary finger used to be watched, so lifting after a pinch read as a tap), started while the map was still gliding (`CameraController.IsGliding`: that touch only stops the map), or lasted over `MaxTapSeconds`.
- **Slop** is `TapGesture.SlopPixels` = max(20 px, 10 dp), about 28 px on a 450-dpi phone (the old fixed 20 px was about 1 mm, so finger jitter dropped real taps). `CameraController.TapThreshold` returns the same value and the camera starts a pan on the same farthest-distance measure, so one press never both pans and taps.
- Deconstruct mode used to act on **press**; it now acts on a tap, so starting a pan over a belt no longer removes it.
- Pure and unit-tested (`TapGestureTests`). The Editor's virtual mouse can't produce a second finger, so the pinch rule is only covered by those tests and on device.

## World-input blocking (taps/pans starting on UI)

`UIInputBlocker` (`Assets/Scripts/UI/UIInputBlocker.cs`) is the single source of truth for "is this screen point over blocking UI". Every world-input consumer routes through it so they all agree:

- `CameraController` — a press whose start point is over UI never begins a pan (`_pressOverUI` gate in `HandleSwipePan`).
- `PlayerInputRouter`, `BuildingPlacementController` (plus its `IsPointerOverPlacementUI` placement-bar test), `ConveyorPlacementController` (plus the conveyor-bar test) and `DeconstructController` — pass it to `InputUtils.PumpTap`, so a press that began over UI is never a tap (`TapGesture`). The router also blocks a tap whose release lands on UI.

How it works: each `UIDocument` self-registers via `UIInputBlocker.Register` in `OnEnable` and unregisters in `OnDisable` (see `HUDController`, `DevConsoleController`) — so consumers need NO scene wiring. `IsPointerOverUI` converts the point with `RuntimePanelUtils.ScreenToPanel` (**no Y-flip** — matches `HUDController.ScreenPointInElement`, the proven convention) and walks each registered panel's tree, testing `worldBound.Contains` on every visible blocking surface. A surface is blocking if it is a `Button`/`Toggle`/`Slider`/`TextField` or carries a class in `BlockingClasses` (e.g. `slide-panel`, `left-drawer`, `top-bar`, `dev-console`, plus the `blocks-world-input` marker class). `display:none` subtrees (closed slide-panels) are pruned so a collapsed panel never blocks. **Do not use `IPanel.Pick` here** — it proved unreliable across the separate HUD and dev-console panels, which is why the hit-test mirrors HUDController's `worldBound`-based `ScreenPointInElement`.

**Modal overlays:** `UIInputBlocker.SetModal(owner, active)` registers a full-screen/debug overlay that blocks *all* world input while open, regardless of pointer position — skip per-element hit-testing entirely. The dev console uses this (`DevConsoleController.SetVisible` / `OnDisable`): it shares the HUD's `PanelSettings` (`gamePanelSettings`), so two `UIDocument`s render into one runtime panel, and per-element `worldBound` hit-testing across that shared panel proved unreliable on-device. A debug console doesn't need precise hit-testing — block everything while it's up. Use `SetModal` for any true modal where "block the whole screen" is acceptable; use the class/`worldBound` path for partial HUD chrome (bars, drawers) that must let the world stay live elsewhere.

**When adding a new full-screen or interactive panel:** give its root the `blocks-world-input` class (or a class already in `BlockingClasses`) so taps/pans on it don't leak to the world — or call `SetModal` if it's a true modal. `IsBlockingElement` and the modal short-circuit are covered by `UIInputBlockerTests` (pure, edit-mode).

## Styling

- `Assets/UI/tokens.uss` — design tokens (colors/spacing/typography vars). `Assets/UI/components.uss` — shared classes. `Assets/UI/GameHUD.uss` — HUD layout. Panel-specific: `AchievementsMenu.uss`, `PremiumShop.uss`.
- **Icons: never use the `✕ ✓ ↻ ⇄` text glyphs.** The Android default font lacks them and they render blank on device (#165). Use `GlyphIcon` (`Assets/Scripts/UI/GlyphIcon.cs`), which is vector-drawn and strokes with the inherited text `color`. In UXML, use `<ui:Button text="" class="close-btn glyph-host"><MobileIdleBuilder.GlyphIcon icon="Close" /></ui:Button>` (`icon` = `Close|Check|Rotate|Flip`). In code, use `GlyphIcon.SetOn(host, kind)` / `ClearFrom(host)` / `TitleRow(kind, label)`. Size it per context with `.<host-class> > .glyph-icon` rules in `components.uss`. `GlyphIconTests` fails if any GameHUD text uses those glyphs. Other symbols (`▶ ○ ⚙`, emoji in notification banners) are still unverified on device.
- **Currency symbols come from our own font.** `◈` entropy, `✦` prestige, `♦` crystals and `⚡` power are drawn glyphs in `Assets/Fonts/CurrencyIcons.ttf`, used through the fallback list in `gamePanelTextSettings` (on `gamePanelSettings`), so they inherit the label's `color` and need no markup: just type the character. **Use `♦` (U+2666) for crystals, never `◆` (U+25C6):** the HUD's default font (NotInter) has `◆`, and a character the default font has never reaches the fallback. To change a shape, see "Currency icons" in `visual-design.md`. `CurrencyIconFontTests` guards this.
- Reuse existing classes (e.g., `upgrade-row`, `upgrade-row--locked`, `slide-panel`) before writing new USS. Grep `GameHUD.uss`/`components.uss` for a class before inventing one.

## Checklist: adding a new panel

1. In `GameHUD.uxml`, copy an existing `slide-panel` block (e.g., `upgrades-panel`: header label, currency label, `ScrollView`) and rename ids.
2. Add a nav `Button` in the `left-drawer` nav scroll (copy `btn-upgrades` markup).
3. New sub-controller class copying `PrestigeShopSubController.cs` (`Init` / `SetECSContext` / `Refresh`).
4. In `HUDController.cs`: add the `GetComponent<>()` field (`:106-111` region), wire the button (`:347-369` region), add the `OpenXPanel` method mirroring an existing one (closes others, removes `hidden`, calls `Refresh()`).
5. Tell the user to add the component to the HUD GameObject in GameScene (manual step).
6. Use `ToastService` for transient feedback, not ad-hoc labels.
   - **Back button (#205):** a new slide panel must be in `_allPanels` (so Android back / Escape closes it). A new modal needs an `IsOpen` + `Close()` and a row in `BackNavigation` (`UI/BackNavigation.cs`, pure, tested) plus the switch in `HUDController.HandleBackButton`. Order: mode active → yield to its controller; dialogue → swallowed (never skipped); confirm prompt; Entropy Surge offer card (minimizes, like its X); idle return; update notice; inspector; panel; drawer; root → nothing.
7. Verify visibility: panel must not be clipped by a zero-height wrapper; check parent sizing classes (CLAUDE.md recurring bug).
8. Mobile: respect safe area (`SafeAreaAdapter` exists; it pads the document root in panel px, never percent, since UI Toolkit resolves percent padding against WIDTH, and paints `safe-area-fill` strips in the top-bar colour behind the top/left/right insets when a `top-bar` exists, framing off the landscape camera cutout). Android does not report rounded display corners as unsafe, so inset edge-to-edge bottom panels from the sides (see `.dialogue-box`); test portrait sizing.

## Pitfalls

- `root.Q<T>("name")` returns null silently for typos — null-check and log, especially in `Init`.
- Per-frame ECS reads belong in `HUDController.Update` flow or `HUDStatusBarController`; panel `Refresh()` is on-open only.
- Don't edit `GameHUD.uss` design tokens for one panel — add a panel-specific USS if needed and register it on the panel root.

- **Recipes tab (#336):** `HUDController.BuildRecipeList` groups known recipes with `RecipeGrouping.Group` (one row per output item). One method renders as before. Several methods render the chosen method's row plus a `recipe-methods-toggle` button ("N ways to make this"); expanded, `recipe-methods` lists every method (`BuildMethodDetailRow`: "Made in a X", inputs, time, lock text, craft buttons). `RecipeGrouping.PickMethod` picks the row's method: the remembered one (`_recipeMethodChoice`, session only, set when a method's craft button is pressed), else the first unlocked menu-craftable one. Rows are code-built; the classes live in `GameHUD.uss`.
- **Item value readouts:** the Recipes group row shows `HUDController.WorthEachText` ("Worth ◈ X each", price from `ItemValue.PricePerItem` = `SurplusSale.DemonPrice`). The inspector adds three fixed rows under "Produces" for crafters (`HUDBuildingInspectorSubController.ValueLines`: worth each, per craft with outMult, per second at current speed) and one `CollectorValueLine` row for collectors. Maths lives in `Services/ItemValue.cs` and mirrors ProductionSystem/CollectorSystem (outMult = manager `AppliedOutputMult` x `GlobalProductionBonus.OutputMult`; speed = `ProductionSpeed` x `PowerStatus.ThrottleRatio` x `GlobalProductionBonus.SpeedMult`). `NumberFormat.Compact`/`Entropy` (UI/NumberFormat.cs) format the numbers.
- **Cyclotron Kick:** drawer button `btn-cyclotron` (hidden until the 2nd prestige) opens `cyclotron-modal` (`idle-return-card` copy, three steps `cyclotron__intro` / `__play` / `__result`; the intro holds `cyclotron__insight` and the two upgrade rows `cyclotron__boost-upgrade` / `cyclotron__cooldown-upgrade`), owned by `CyclotronController` (added in `HUDController.Awake` with `GetComponent ?? AddComponent`). The play area is `CyclotronView`, a Painter2D `[UxmlElement]`. Back shares the Surge-offer layer; the modal counts toward `HUDController.MenuOpen`. Details: `tasks/feature-cyclotron-kick.md`.
