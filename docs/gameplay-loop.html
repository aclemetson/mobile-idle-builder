Scene Flow

The game is a single gameplay scene. The main menu has been removed; startup goes directly through a placeholder splash into the game:

  1. SplashScreen (build index 0) — shows title/logo for 2 s, then calls SceneLoader.GoTo("GameScene").
  2. LoadingScreen (build index 1) — async asset load + ECS SubScene init (waits for ECSLoadBridge.IsLoaded).
  3. GameScene (build index 2) — the only persistent gameplay scene.

All former main-menu functionality lives in the HUD:

  • Leaderboard — Competition panel, btn-pvp in the drawer.
  • Achievements — Achievements panel, btn-achievements in the drawer.
  • Shop — Premium Shop panel, btn-shop in the drawer (HUDPremiumShopSubController).
  • Settings — Settings panel, btn-settings ⚙ in the top bar (HUDSettingsSubController).

Field Collection (Tap + Cooldown)

Quantum fields are tap-to-collect. Each tap on a field yields one item (weighted by the field's drop table) and puts that field on a short cooldown — there is no longer any "active field" continuous auto-collection. A small radial wheel appears above the tapped field and empties clockwise like a clock; the field cannot be tapped again until the wheel runs out (ManualFieldCollector + FieldCooldownIndicator).

  • Base cooldown = FieldSO.tapCooldownSeconds (1.5 s by default).
  • Persistence — the cooldown is stored as a UTC timestamp, so it keeps ticking while the app is closed and cannot be reset by quitting and relaunching. A cooldown that fully elapsed while away is simply ready on return.
  • Effective cooldown = base × researchMult × (1 − prestigeReduction), floored at 0.25 s.

Two upgrade tracks shorten the cooldown and stack multiplicatively:

  • Research (per run): Rapid Extraction I (−15%) → Rapid Extraction II (−20% more), via ResearchSO.fieldCooldownMult.
  • Prestige (permanent): Quick Hands — −5% per level, max −50% (UpgradeEffectType.FieldCooldownReduction).

Note: the Harvester building still auto-collects from a field continuously — that is a separate, automated system (CollectorSystem) and is unaffected by the manual tap cooldown.

Visual feedback. Each field is drawn as a wire-mesh overlay across its 1x1 tile — a "mathematical field" grid whose lines fluctuate with noise (FieldWireMesh + the MobileIdleBuilder/FieldWireMesh shader). There is no longer a continuous ambient particle stream; instead a tap bounces the mesh and births a short particle burst from the tile (FieldEffect.Burst), so collection always reads as a deliberate hit.

Conveyor Placement (Mobile)

Conveyors use a deliberate, tap-based flow (not press-drag) so a stray touch can never drop an abandoned belt. Opening the Conveyor card enters the mode in Create; the camera still pans on drag, and only taps that stay under the pan threshold register.

  1. Tap a start tile (any free cell or an existing belt) — it marks the run's start.
  2. Tap a destination (another free / belt cell). The best route is drawn as a ghost: a single-turn L when possible, otherwise routed around obstacles with as few turns as possible (ConveyorPathfinder).
  3. ↻ Bend flips which way the L turns · ✓ Place commits the run · ✕ Clear drops the pending end (keeping the start).
  4. After placing, the run's end becomes the next start, so you can keep extending. Finished (formerly "Cancel") exits the mode.

The Mode: Create / Mode: Destroy toggle sits next to Finished and always starts on Create. In Destroy, tapping a belt removes that single segment (its chain neighbours re-link via ConveyorPlacer.RemoveSegmentAt, shared with the global Deconstruct tool). Toggle back to keep building.

River-flow visuals. Belts render as a flowing "river" ribbon (custom MobileIdleBuilder/ConveyorFlow shader on a procedural strip mesh) whose current scrolls toward the output — the flow direction reads straight from the moving water, no arrows.

Merging. A run can flow into an existing belt: a grid cell may take flow from 2 or 3 inbound sides into its single output (a cell may merge inputs but never fork its output — that placement is rejected). When several streams are ready at once the inbound sides take turns (round-robin via MergeCursor) so no branch starves, and the merge junction visibly converges. Connectivity is derived from each cell's output direction by ConveyorPlacer.RelinkAll, so merges survive save/load and feed offline production unchanged.

Auto-turn into buildings. A run that ends next to a building input (or starts next to an output) auto-orients its end so the current flows into / out of the building, turning 90° when needed (ConveyorPlacer.TryAutoTurnEnds).

Power Grid (Connection Range + Overlay)

Power buildings (the Basic Generator and the Power Relay) form a connected grid, not a set of independent coverage circles. Each power building has a link range (tiles), and two of them connect when their footprint distance is within the larger of the two link ranges. A building extends the grid only if it is a generator or chains, link by link, back to one.

  • Generators produce eV into a single shared pool and cover a small influence radius (2→5 tiles across L1–L4) with a short link range (4→7).
  • Power Relays produce no eV; they re-radiate the shared pool over a large influence radius (5→8) and reach far with a long link range (6→9). A relay that is out of link range of every generator is stranded: it is not on the grid and powers nothing — so relays must be placed to chain back to a generator (directly or through other relays).

Seeing the connections. While positioning a power building, dashed lines preview which existing power buildings it would link to (they disappear once placed). Selecting a placed power building shows the same dashed links plus its influence ring. A ⚡ toggle in the top bar turns the whole-map power overlay on (bright bolt — all links drawn amber for wired / grey for stranded clusters, plus a coverage ring around every powered building) or off (grey bolt, overlay hidden); the choice persists across sessions.

Implemented in PowerGridSystem (connectivity flood → PowerNodeData.IsGridLinked), shared math PowerCoverageMath.NodesLinked, and the PowerConnectionGraph/PowerConnectionRenderer/PowerConnectionOverlayController visualization. Power state is not saved — it recomputes from building positions/levels on load.

Session Authentication

Google Sign-In uses a silent-first strategy backed by two device-local timestamps (PlayerPrefs — not cloud-synced):

  • Last app open — recorded every launch; triggers interactive sign-in if ≥ 30 days have passed (inactivity rule).
  • Last full auth — recorded only after the user completes the Google account picker; triggers interactive sign-in again once ≥ 90 days have passed (mandatory re-verification).

Under normal use (daily or weekly play) neither threshold is reached and the account picker is never shown after the first login. Implemented in AuthSessionPolicy + GoogleSignInBridge. Auth fires transparently during GameScene startup — there is no separate login screen.

Building Upgrade System

Each building has two independent upgrade tracks. Both tracks have 3 purchasable levels (L2/L3/L4) and reset on prestige.

Speed Upgrades

Increases production throughput.
Pattern: L1=1× → L2=2× → L3=4× → L4=8× (each upgrade doubles speed). Cost multiplier: ~4–5× per level.
Affects active and idle play equally.

Storage Upgrades

Increases the output buffer (items held before stalling). Benefits idle/offline play. Cost ≈60% of equivalent speed upgrade.
Buffer sizes: base 10–30 → L2 75–300 → L3 375–1500 → L4 2500–4000.

Two-Buffer Model (processing buildings)

Input buffer: 30 items per slot (fixed) — upstream conveyor stops when full.
Output buffer: upgradeable — production stalls when full (no downstream conveyor or backup).

Successive Purchase Scaling

Each additional placement of the same building type costs more:
Tier 1: ×1.5 per purchase · Tier 2: ×1.4 per purchase · Tier 3+: ×1.3 per purchase.
Formula: cost(n) = base × multiplier^(n−1)

✓ Implemented: Both speed and storage upgrade tracks are purchasable in the building inspector panel. Upgrade levels persist across sessions (save/load) and are reflected in production speed and output buffer capacity immediately on purchase.

Planned (not yet implemented): place_extras_in_inventory research — when output buffer is full, items go to inventory instead of stalling. sell_excess_inputs research — auto-sell input overflow for 25% of base value.

Idle Collection

When the player closes the app, the whole production network keeps running in the background — up to a capped window. The offline model walks the grid as a directed graph: collectors are sources, recipe buildings ("synthesisers") are input-limited (they craft only as fast as their incoming items allow), and entropy sinks (Maxwell's Demon) convert whatever reaches them to currency. So a chain like Harvester → Combiner → Maxwell's Demon now correctly banks the value of the synthesised item (e.g. Hydrogen), bounded by the upstream collector's real throughput so it can never over-credit.

How Chains Are Detected

On every auto-save, pause, and quit the game analyses the saved grid to build a production-graph snapshot:

  1. Each saved conveyor is an edge: the building adjacent to its head is the producer, the building adjacent to its tail is the consumer (or nothing → player inventory).
  2. Collectors (Placement Rule = Must Be On Field) produce their field item at a fixed rate. Recipe buildings compute an output rate = min(craft rate, what their incoming items sustain), resolved in dependency order so upstream feeds downstream.
  3. Each terminal flow is credited once:
    • Into an Entropy Sink (Maxwell's Demon) → produces entropy from that item's sell value on return.
    • Into no building → items go to player inventory.

Internal producer→synthesiser edges are consumed (not double-counted). If a synthesiser ends up starved (an input it needs never arrives, so it produces nothing), the item feeding it is credited to inventory instead — a non-regressive fallback so no offline output is ever silently lost. Power is not modelled offline (synthesisers are assumed powered). The snapshot is rebuilt whenever buildings or conveyors change.

Welcome Back Modal

Shown once per session immediately after the save loads (after IsLoaded = true in ECSLoadBridge). Dismissed by tapping Claim. Not shown if no chains were active or earnings were zero.

  • Time-away line: "Away 3h 24m · collected 2h 0m (cap reached)" when capped, or "Away 45m" when under cap.
  • Item list: one row per item type with quantity.
  • Entropy line: "◈ +1,250 entropy" if any entropy was earned from entropy-sink chains.

Idempotent: the idleCollectionApplied field in SaveData prevents double-application if cloud reconciliation swaps in a newer save mid-session.

Continuous Motion on Return (Belt Priming)

The Welcome Back payout answers how much was produced while away, but the belts themselves reload empty (only chain geometry is saved, never the items riding them). To keep the illusion that automation never stopped, each restored collector chain is re-seeded with in-transit items the moment the grid loads, so belts read as full and flowing on the first frame instead of visibly re-filling from the harvesters.

  • Where: BeltPrimer.PrimeAllChains, called once from GridSaveService.LoadGrid() after conveyors are restored. Background → foreground does not reload the grid (belts stay live), so there is no re-prime path.
  • Spacing: one item per cell, spaced by the feeding collector's steady-state cadence — step = round( (1 / effectiveRate) / transportTime ) cells, capped at one item per cell when the collector saturates the belt.
  • Rate: the same global speed multipliers the idle snapshot uses (prestige × megastructure × premium boost) fold into the spacing.
  • Presentation only: primed items are ordinary cargo that flow to their sink / inventory normally. Their count is bounded by belt length, so any entropy they add at the sink is negligible next to the offline payout. First-ever sessions (tutorial-skip preset) are not primed — a new factory starts empty.

  6. Claim All button claims every pending reward in the active tab at once

New Trigger Types

  • Login — fires once per game session start (called by AchievementService.NotifyLogin() from SaveManager)
  • SpendEntropy — delta = amount spent per transaction (call NotifyEntropySpent(amount) from entropy spend sites)
  • TotalPrestigeCurrencyEarned — delta = PC earned per prestige (call NotifyPrestigeCurrencyEarned(amount) from PrestigeSystem)

Hook-Up Checklist (connect Notify* calls in gameplay code)

  • NotifyLogin() → call from SaveManager.Start() or GameBootstrap once per session
  • NotifyCraft(itemId, qty) → already called from ManualCraftService; ensure ProductionSystem also calls it per automated output
  • NotifyBuildingPlaced(type) → call from BuildingPlacementController.OnBuildingPlaced
  • NotifyResearchCompleted(id) → called from ResearchService.CompleteResearch() (when the research timer finishes / is skipped)
  • NotifyPrestige() → call from PrestigeSystem after reset completes
  • NotifyEntropySpent(amount) → called from ResearchService.Purchase() (entropy paid up front when research starts) and building placement cost deduction
  • NotifyPrestigeCurrencyEarned(amount) → call from PrestigeSystem when PC is calculated
  • NotifyTierReached(tier) → call when PlayerProgressData.CurrentTier increments
  • NotifyPVPWin() → call from PVPService on match completion
  • NotifyCodexUnlocked(total) → call when a new codex entry is discovered

Premium Shop — Entry & Currency

Accessible from the Main Menu via the ◆ SHOP button. To reach it from an active run, use the ⬅ Go Back button in the game HUD top bar (this saves the run first). The shop is not embedded in the game scene.

  • Crystal balance: SaveData.paidCurrency — earned from achievements, bought via IAP
  • Speed Boost state: SaveData.speedBoostExpiryUtc (ISO 8601 UTC expiry)
  • Net Worth snapshot: SaveData.lastKnownNetWorth — written by ECSLoadBridge.FlushToSave() on each save; used by Entropy tab pricing
