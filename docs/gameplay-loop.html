Session Authentication

Google Sign-In uses a silent-first strategy backed by two device-local timestamps (PlayerPrefs — not cloud-synced):

  • Last app open — recorded every launch; triggers interactive sign-in if ≥ 30 days have passed (inactivity rule).
  • Last full auth — recorded only after the user completes the Google account picker; triggers interactive sign-in again once ≥ 90 days have passed (mandatory re-verification).

Under normal use (daily or weekly play) neither threshold is reached and the account picker is never shown after the first login. Implemented in AuthSessionPolicy + GoogleSignInBridge.

Building Upgrade System

Each building has two independent upgrade tracks. Both tracks have 3 purchasable levels (L2/L3/L4) and reset on prestige.

Speed Upgrades

Increases production throughput.
Pattern: L1=1× → L2=2× → L3=4× → L4=8× (each upgrade doubles speed). Cost multiplier: ~4–5× per level.
Affects active and idle play equally.

Storage Upgrades

Increases the output buffer (items held before stalling). Benefits idle/offline play. Cost ≈60% of equivalent speed upgrade.
Buffer sizes: base 10–30 → L2 75–300 → L3 375–1500 → L4 2500–4000.

Two-Buffer Model (processing buildings)

Input buffer: 30 items per slot (fixed) — upstream conveyor stops when full.
Output buffer: upgradeable — production stalls when full (no downstream conveyor or backup).

Successive Purchase Scaling

Each additional placement of the same building type costs more:
Tier 1: ×1.5 per purchase · Tier 2: ×1.4 per purchase · Tier 3+: ×1.3 per purchase.
Formula: cost(n) = base × multiplier^(n−1)

✓ Implemented: Both speed and storage upgrade tracks are purchasable in the building inspector panel. Upgrade levels persist across sessions (save/load) and are reflected in production speed and output buffer capacity immediately on purchase.

Planned (not yet implemented): place_extras_in_inventory research — when output buffer is full, items go to inventory instead of stalling. sell_excess_inputs research — auto-sell input overflow for 25% of base value.

Idle Collection

When the player closes the app, harvesters keep running in the background — up to a capped window. Only direct collector chains are simulated: Harvester → Conveyor → (Inventory or Maxwell's Demon). Recipe-based synthesisers mid-chain are paused; the UI discloses this.

How Chains Are Detected

On every auto-save, pause, and quit the game analyses the saved grid to build a chain snapshot:

  1. Walk each saved conveyor chain (head→tail).
  2. The building one step upstream of the chain head must be a collector (Placement Rule = Must Be On Field).
  3. The building one step downstream of the chain tail is checked:
    • If it is an Entropy Sink (Maxwell's Demon) → chain produces entropy on return.
    • Otherwise → items go into player inventory.

The snapshot is rebuilt whenever buildings or conveyors are placed or removed.

Welcome Back Modal

Shown once per session immediately after the save loads (after IsLoaded = true in ECSLoadBridge). Dismissed by tapping Claim. Not shown if no chains were active or earnings were zero.

  • Time-away line: "Away 3h 24m · collected 2h 0m (cap reached)" when capped, or "Away 45m" when under cap.
  • Item list: one row per item type with quantity.
  • Entropy line: "◈ +1,250 entropy" if any entropy was earned from entropy-sink chains.

Idempotent: the idleCollectionApplied field in SaveData prevents double-application if cloud reconciliation swaps in a newer save mid-session.
